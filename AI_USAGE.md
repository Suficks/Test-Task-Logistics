# AI Usage

Документ о том, как в этом тестовом задании использовался AI (Cursor), какие решения принимались самостоятельно, и что осталось улучшить.

## Какие части делались с AI

AI помогал ускорить рутину и черновую реализацию:

- первичная генерация OpenAPI-типов и каркас MSW / моков
- черновики UI страниц (список, деталка, ставки) на Ant Design
- boilerplate page models, query/mutation-обёрток, seed-данных
- вынос дублей в shared (`Panel`), виджет списка, фичу ставки
- минимальные unit-тесты (Vitest) и черновик README
- быстрый поиск по коду, правки по замечаниям, мелкий рефакторинг

AI использовался как ассистент «наборки и итераций», а не как источник финальных архитектурных решений.

## Какие решения кандидат принял сам

Базовую настройку инструментов и архитектуру проекта выстраивала самостоятельно:

- выбор и связка стека: Vite, TanStack Router/Query, MobX, RHF + Zod, MSW, Ant Design
- FSD-раскладка слоёв (`app` / `pages` / `widgets` / `features` / `entities` / `shared`) и границы ответственности
- явные DTO и фабрики в `entities` (auction / bet), без опоры на сгенерированную OpenAPI-схему как на доменную модель
- паттерн моков: `generate()` + in-memory CRUD + handlers, которые реально меняют состояние после mutations
- page models: `queryClient` через хук, api внутри модели
- фильтры в URL + Zod search params, модель списка не пересоздаётся на каждый search
- визуальный язык: тени через theme tokens, светлая тема, без «AI-фиолетового» дефолта
- решение, что уходит в `features/set-bet` и `widgets/auctions-list`, а что остаётся в pages
- критерии проверки результата и содержание README / этого файла

## Какие AI-предложения были отклонены

Не всё из предложений AI принималось:

1. **Типы «прямо из OpenAPI-схемы» как доменные DTO**  
   AI предложил брать типы из `openapi-typescript` / `components['schemas']`. Так не делала: схема — контракт API, доменные DTO и фабрики живут явно в `entities`.

2. **Некорректное размещение по папкам и слоям FSD**  
   Часть кода AI клал «куда удобнее» (толстые pages, смешение feature/widget/entity). Перекладывала и ограничивала зависимости по правилам слоёв.

3. **Внешнее представление информации**  
   Отклоняла/правила перегруженные куски UI (например, сырой текст «Сцепка: — · …»), лишние акценты.

4. **Слабая декомпозиция**  
   AI часто оставлял монолитные страницы. Настаивала на выносе секций, shared `Panel`, feature ставки, widget списка, чистых мапперов/схем для тестов.

5. **Ранжирование ставок «новая всегда лидирует»**  
   В моке `setBet` AI всегда ставил новую ставку на 1 место. Это неверно для аукциона на понижение/повышение — места должны пересчитываться по цене. Исправлено после ручной проверки в UI (см. ниже).

Также не принимала подходы вроде жёсткой привязки модели к route loader / AppConfig, если они усложняли жизненный цикл без выигрыша.

## Какие места кандидат проверял особенно внимательно

- **Модели и слой данных**: page models, invalidate после `setBet`, согласованность list / detail / bets, поведение MSW store (цена, статус, история ставок, 422)
- контракты запросов/ответов относительно OpenAPI (nullable, enum, edge cases вроде `hide_bets_history`, `can_set_bet`)
- Zod для search params и схемы ставки (min / max / step)
- границы FSD после рефакторинга (pages не «протекают» в widgets/features наоборот)
- ручные сценарии в UI: фильтры + URL, ставка, скрытая история, empty/error/skeleton
- **ранжирование истории ставок после `setBet`**: места должны считаться по цене (Down — дешевле выше, Up — дороже выше), а не «новая ставка всегда первая»

## Баг ранжирования ставок (найден при ручной проверке)

При обновлении ставки с более высокой ценой (аукцион на понижение) своя ставка оставалась на 1 месте, хотя у других участников цена была ниже.

**Причина:** в AI-черновике мока `setBet` новая ставка всегда получала `place: 1` и вставала в начало списка; остальные места просто сдвигались (`index + 2`) без пересчёта по цене. Статус всегда становился `Leading`.

**Исправление:** пересчёт мест по цене с учётом типа аукциона (`Down` / `Up`), при равенстве — более ранняя ставка выше; `current` / `available` и статус `Leading` / `Losing` берутся от лидирующей ставки, а не «вслепую» от только что отправленной.

Баг поймала сама на ручном сценарии в UI; правку мока делала с AI.

## Какие риски остались

- MSW in-memory: состояние не переживает reload; нет настоящего backend
- нет e2e; регрессии UI ловятся в основном вручную
- часть полей OpenAPI есть в DTO/моках, но не раскрыта в отдельный продуктный UX
- при росте фич page models могут разрастись — понадобится более жёсткое дробление на features

## Что бы улучшила при наличии ещё одного дня

- добавить e2e на ключевые сценарии (список → деталка → ставка)
- персист моков (например, localStorage) для удобной демо-сессии
- чуть сильнее покрыть тестами маппинг ошибок 422 → поля формы
- полирнуть адаптив и a11y (фокус, клавиатура, контраст)
